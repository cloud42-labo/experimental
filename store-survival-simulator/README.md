# 未来の店舗生存サバイバルゲーム — README

e-Statの実際の国勢調査データ（地域メッシュ統計、令和2年・平成27年、1kmメッシュ）を使い、
出店した店舗が10年後の人口動態と噛み合っているかを「ヒト（客層・採用）」
「モノ（商品・DX）」「カネ（財務健全性）」の観点で定性診断するゲーム。④経営判断の競合密度には
経済センサス‐活動調査（平成28年・産業大分類別、同じ1kmメッシュ）を併用する。**日本全国どこでも**使える
（千葉市稲毛区限定だった旧版からの変更点は後述）。

## `index.html` と `prototype.html` の違い

- **`index.html`** — 現在使う本番用ファイル。`APP_VERSION`定数でバージョン管理
  している（`CLAUDE.md`の「バージョニング」参照）。今後の修正・機能追加はこちらに行う。
- **`prototype.html`** — ここまでの試作過程のスナップショットとして凍結した記録。
  以後は更新しない。

## 動かし方

`index.html` をブラウザで開く（ビルド・サーバー不要）。最初の画面で

1. **店舗の場所**（Google MapsのURL、または「緯度, 経度」）
2. **業種**（8業種から1つ選択。必須 — 未選択だと開始できない。商圏半径の初期値もここで
   決まるが、後から自由に調整できる）
3. **店舗プロファイル（任意）** — 年間売上高・粗利額・販管費（万円）、正社員数・
   パート・アルバイト数、築年数。営業利益と営業利益率は自動計算してゲーム画面に常時表示し、
   パート・アルバイト数は労働力充足診断に、営業利益率・築年数は経営判断診断に使用する
4. **自分自身の e-Stat アプリケーションID（APIキー）**

を入力すると、その場でブラウザが店舗周辺（半径5km分を先読み）の地域メッシュ統計・
経済センサス（競合密度の概算、平成28年）を直接取得する。キーはメモリ保持のみで、
リロードすると再入力が必要。取得後は地図上で位置の微調整、ヒト・モノ・カネコマンドの
適用、5択の経営判断の評価ができる。業種・店舗プロファイルはゲーム画面の「店舗プロファイル」
カードの「編集」からいつでも変更できる。

> **検証結果（2026-07-26、実機Chrome）**: `api.e-stat.go.jp`（`getStatsList` /
> `getStatsData`）はブラウザからの直接fetchが通ることを確認済み。一方
> `www.e-stat.go.jp/gis/statmap-search/data`（町丁目境界shapefileの配信元）は
> `Access-Control-Allow-Origin` を一切返さず確実にCORSブロックされる（回避不可）。
> このため**町丁目の実際の境界ポリゴンは採用せず**、境界データを一切必要としない
> 「JIS地域メッシュ（1km四方の正方形グリッド、緯度経度から数式で計算できる）」を
> 採用した。これにより全国対応とCORS回避を両立している。

## 地域メッシュ統計特有の癖（実装上、要注意）

- **統計表IDが1次メッシュ地域（約80km四方）ごとに別々**。町丁目統計のような
  固定IDが1つあるわけではなく、店舗の座標から該当する1次メッシュコードを計算し、
  `getStatsList`（`searchKind=2`必須）でその都度検索して統計表IDを見つける
  実装になっている（`index.html`内 `findMeshTableId()`）。
- **年齢区分のcat01コードが年度によってズレる**（例:「65歳以上」が2015年は
  `0160`、2020年は`0190`。2020年に「18歳以上」区分が追加されたため後続コードが
  ずれた）。そのためコード番号ではなく、分類名の部分一致（「０～１４歳」
  「１５～６４歳」「６５歳以上」）で該当コードを探す実装にしてある
  （`findCat01Code()`）。
- 年齢区分は「年少(0-14)・生産年齢(15-64)・老年(65+)」の3区分のみ（町丁目統計に
  あった5歳階級別の細かい区分は無い）。旧稲毛区版が使っていた「15-24歳の若年
  労働力」という概念はこのデータでは表現できないため、`laborDependency:"young"`
  は生産年齢人口全体（15-64歳）を労働力プールとみなす扱いに変更した。

## 動作の仕組み(データ取得)

1. 店舗座標から半径5km分のbboxをカバーする1kmメッシュコードを数式で列挙する
   （`meshCodesInBBox()`。境界データ取得は一切不要）。
2. メッシュコードを1次メッシュ地域ごとにグループ化し、地域ごとに
   `getStatsList`で統計表ID（令和2年・平成27年それぞれ）を検索する。
3. 見つかった統計表IDに対し、`getStatsData`（`cdArea`で該当メッシュのみに
   絞り込み、50件ずつバッチ処理）を呼び、人口・年齢3区分の値を取得する。
4. 2015→2020の実測変化率を計算し、対応データがないメッシュ（非居住・秘匿等）は
   商圏内の人口加重平均でフォールバックする。

`scripts/download_boundary.py` / `scripts/build_geojson.py` は、旧稲毛区限定版
（町丁目境界＋小地域統計）が使っていたオフライン生成スクリプトの名残。現在の
`index.html`は実行時にこれらの出力を使わない（参照実装として残置）。

## ドキュメントの経緯

このディレクトリには企画段階のドラフトが複数残っており、内容がそれぞれ
矛盾する。**PRD/GDDは企画時点のアイデア出しの記録であり、最終仕様書ではない。**
実際に何が動くかは `index.html` を正とする。読む順序と変遷は以下の通り。

1. **`store-survival-simulator-spec.md`**（最初のインセプションデッキ＆PRD）
   出店時点の分析ツールという構想。円建てのP&L予測（売上・原価率・人件費率）、
   MapLibre/D3.js + FastAPI + SpatiaLiteという技術スタックを提案していた。
   千葉市稲毛区の町丁目境界を前提としていた。

2. **`store-survival-simulator-design-doc.md`**（上記の実装設計書・旧版）
   spec.md の技術的な穴を埋めるための設計書。SpatiaLite前提はそのまま
   踏襲していた。→ **実装に合わせて全面的に書き直し済み**（後述）。

3. **`store-survival-game-gdd-v6.md`**（GDD v6、v6.1改訂を含む）
   「分析ツール」から「サバイバルゲーム」路線に転換。7業種に拡張。
   **v6.1で円建てのP&L・カネコマンドを廃止**し定性診断のみに変更。技術スタックも
   Streamlit + PyDeck + 標準SQLite + JISメッシュ座標計算（SpatiaLite不要）に
   変更する方向で書かれている——結果的に、最終的に実装された「メッシュベース・
   SpatiaLite不要」という方向性はこのGDDが最初に示していたものと一致した。

4. **実際に実装されたバージョン**（`index.html`。旧`prototype.html`から派生・凍結）
   当初は千葉市稲毛区限定・町丁目境界データをHTMLに同梱する方式だったが、
   「研修本番は全国が対象。店舗座標を起動画面で入力してもらえばよい」という
   方針転換を受け、**JIS地域メッシュ統計（1kmメッシュ）ベースの全国対応版**に
   刷新した。境界ポリゴン（shapefile）はCORSで確実にブロックされることが
   実機検証で判明したため不採用とし、代わりに数式のみで座標が求まるメッシュ
   グリッドを採用している。
   - バックエンド・DBは無し。参加者が起動画面で店舗座標とe-Stat
     アプリケーションIDを入力し、その場でブラウザが地域メッシュ統計を
     直接fetchする（キーはメモリ保持のみ、配布ファイルにも埋め込まない）。
   - フロントエンドは Leaflet.js + Turf.js による**静的HTML1ファイル**
     （Streamlit/PyDeckでもMapLibre/D3でもない）。
   - 診断ロジックはGDD v6.1の方針（実人口データのみ・お金の計算をしない）
     を踏襲しているが、判定は「良好／注意／深刻」の3段階（GDDの本文にある
     4段階・1.1/0.9/0.7の閾値ではなく、実装では1.0/0.8の2閾値）。
   - その後、店舗プロファイル（財務・築年数）、経済センサスによる競合密度の概算、
     5択の経営判断（保全/改装/商圏拡大/競合対応/撤退）の妥当性診断を追加した。
     GDD v6.1が「一旦削除」としたカネコマンドも、円建てP&Lとしてではなく
     「財務健全性の判定を定性的に1段階動かすコマンド」という形で限定的に復活している。
     詳細は`store-survival-simulator-design-doc.md`参照。
   - GDDが描いていた「実際の円建てでの10期P&Lシミュレーション」「SSS〜Eの生存ランク」
     「ポータブルZIP配布」は未実装。

つまり、実装は当初spec.mdの「実際の町丁目境界を使う」路線で始まったが、CORS制約と
全国対応の要求から、GDD v6が最初に提案していた「メッシュベース・SpatiaLite不要」
路線に回帰する形に落ち着いた、という経緯。

## 配布方式（v0.10.0で変更）

**参加者はURLを開くだけ。e-Statのアプリケーションキーは要らない。**

v0.9.0までは、参加者それぞれが自分のe-Stat アプリケーションIDを取得して起動画面へ入力し、
ブラウザから直接 `api.e-stat.go.jp` を叩く方式だった。研修配布を前提にすると次の3点で無理が
あったため、**統計データを事前に取得して同梱する方式**へ変えた。

1. 参加者全員にe-Statの登録をしてもらう必要があり、当日の導入コストが高い
2. キーがクライアントに存在する以上、共有・貸与PCでの残留リスクが消えない
   （キーを保存して次回自動入力する案＝PR #73 は、この方式変更により不要になり取り下げた）
3. 参加者が同時にe-Statを叩いたときのレート制限が未検証のリスクとして残る

事前生成データの形式と作り方は [data/areas/README.md](data/areas/README.md) を参照。
オーナーが自分のキーで研修対象エリアを事前に書き出しておき、参加者は一覧から選ぶだけ。

任意座標のライブ取得は「別の場所を診断する」として残しているが、既定では折りたたまれており、
**キーの保存は一切行わない**（リロードで消える）。

## ステータス

`index.html`が本番、`prototype.html`は凍結済みの過去スナップショット。

**研修利用前に確認すること**:
- 研修で使うエリアを事前に書き出し、`data/areas/` と `index.json` へ反映しておく。
  一覧が空だと参加者は開始できない（起動画面がライブ取得の案内へ切り替わる）。
- Leaflet / Turf を unpkg（CDN）から読み込んでいるため、**会場のネットワークがCDNへ
  到達できないと地図が出ない**。配布前に会場回線で一度開いて確認する
  （恒久対策としてライブラリの自己ホストが要る。下記「未確認・残課題」参照）。
- `api.e-stat.go.jp` へのブラウザからの直接fetchは実機で成功を確認済み
  （2026-07-26、Chrome）。これはライブ取得（エリア書き出し）を使うときだけ関係する。
- 地域メッシュ統計は町丁目統計と違い1次メッシュ地域ごとに統計表IDが異なるため、
  ライブ取得では「取得中…」の待ち時間が数十秒程度かかることがある。事前生成データを
  選んだ場合は即時。

**未確認・残課題**:
- Leaflet / Turf の自己ホスト。開発サンドボックスはunpkgへの到達がネットワークポリシーで
  遮断されており、ライブラリを取り込めなかったため未実施。自己ホストすれば会場回線への
  依存が消え、ページ内で動く第三者スクリプトも無くなる。
- 事前生成データを使った通しの実機確認（地図描画を含む全体）。上記CDN遮断のため、
  このサンドボックスでは起動画面とデータ読み込み経路までしか検証できていない。
