# 未来の店舗生存サバイバルゲーム — README

千葉市稲毛区の実際の国勢調査データ（2015年・2020年、町丁目単位）を使い、
出店した店舗が10年後の人口動態と噛み合っているかを「ヒト（客層・採用）」
「モノ（商品・DX）」の観点で定性診断するプロトタイプ。

## 動かし方

`prototype.html` をブラウザで開く（ビルド・サーバー不要）。最初の画面で
**自分自身の e-Stat アプリケーションID（APIキー）** を入力すると、その場で
ブラウザが e-Stat から町丁目境界データと国勢調査人口データを直接取得する
（キーはメモリ保持のみ、リロードすると再入力が必要）。取得後、地図上で
店舗位置をクリックし、業種を選ぶと商圏内の実人口10年推移と戦略適合度が
表示される。

> **⚠ 未検証の前提**: e-Stat API・境界データ配信元がブラウザからの直接fetch
> （CORS）を許可しているかは、このリポジトリの開発環境からは検証できていない。
> 研修本番の前に、実際のブラウザで一度通しで動作確認すること。

`scripts/download_boundary.py` / `scripts/build_geojson.py` は、上記のライブ
取得を実装する前の開発時に使っていたオフライン生成スクリプト（`data/inage_ku.geojson`
を作る）。現在の `prototype.html` はこれらの出力に依存していないが、ロジックの
リファレンス実装として残してある。

## ドキュメントの経緯

このディレクトリには企画段階のドラフトが複数残っており、内容がそれぞれ
矛盾する。**PRD/GDDは企画時点のアイデア出しの記録であり、最終仕様書ではない。**
実際に何が動くかは `prototype.html` と `scripts/` を正とする。読む順序と
変遷は以下の通り。

1. **`store-survival-simulator-spec.md`**（最初のインセプションデッキ＆PRD）
   出店時点の分析ツールという構想。円建てのP&L予測（売上・原価率・人件費率）、
   MapLibre/D3.js + FastAPI + SpatiaLiteという技術スタックを提案していた。

2. **`store-survival-simulator-design-doc.md`**（上記の実装設計書・旧版）
   spec.md の技術的な穴（境界ポリゴン取得パイプライン未定義、DBスキーマの
   正規化不備など）を埋めるための設計書として書かれた。SpatiaLite前提は
   そのまま踏襲していた。→ **今回、実装に合わせて全面的に書き直し済み**
   （後述）。

3. **`store-survival-game-gdd-v6.md`**（GDD v6、v6.1改訂を含む）
   「分析ツール」から「サバイバルゲーム」路線に転換。7業種に拡張
   （ペット関連小売・金融事業を追加）。**v6.1で円建てのP&L・カネコマンドを
   廃止**し、「実データにない数値で儲かる/儲からないを見せると本質が伝わらない」
   という理由で定性診断のみに変更。技術スタックもStreamlit + PyDeck +
   標準SQLite + JISメッシュ座標計算（SpatiaLite不要）に変更する方向で
   書かれている。

4. **実際に実装されたプロトタイプ**（`prototype.html`）
   上記のどちらとも技術的には異なる、もっと簡素な構成になっている。
   - バックエンド・DBは無し。研修での配布形態が「HTMLファイル単体」という
     制約に合わせて、**参加者が自分の e-Stat アプリケーションIDを起動画面で
     入力し、その場でブラウザが e-Stat から境界データ・人口統計データを
     直接fetchする**設計（キーはメモリ保持のみ、配布ファイルにも埋め込まない）。
   - フロントエンドは Leaflet.js + Turf.js + shpjs（shapefile ZIPをブラウザで
     GeoJSON化するライブラリ）による**静的HTML1ファイル**
     （Streamlit/PyDeckでもMapLibre/D3でもない）。
   - 診断ロジックはGDD v6.1の方針（実人口データのみ・お金の計算をしない）
     を踏襲しているが、判定は「良好／注意／深刻」の3段階（GDDの本文にある
     4段階・1.1/0.9/0.7の閾値ではなく、実装では1.0/0.8の2閾値）。
   - GDDが描いていた「10期のP&Lシミュレーション」「SSS〜Eの生存ランク」
     「ポータブルZIP配布」は未実装。
   - `scripts/` はこのライブ取得ロジックを組む前の開発時に使っていたオフライン
     版（事前にgeojsonを1回だけ生成する方式）の名残で、現在は実行時に使われない。

つまり、実装は spec.md（実際の境界ポリゴンを使う点）とGDD v6.1（財務モデルを
持たない定性診断である点）の両方から要素を引き継ぎつつ、どちらの技術スタックも
採用せず、「HTML単体で配布し、各参加者が自分のAPIキーでその場からデータを
取得する」という研修向けの制約に合わせた形に落ち着いた、という経緯。

## ステータス

千葉市稲毛区限定のプロトタイプ。他エリア対応や継続開発の予定は未定
（`CLAUDE.md` の方針通り、ここは試作置き場）。

**研修利用前に必ず確認すること**:
- e-Stat API（`api.e-stat.go.jp`）と境界データ配信元（`www.e-stat.go.jp/gis/...`）が
  実際にブラウザからのCORSを許可するか、本番想定のネットワークで一度確認する。
- 参加者ごとに自分のe-Stat アプリケーションIDが必要（未発行者は事前にe-Statマイページで
  取得してもらう）。
- shapefile ZIPは千葉県全域分のダウンロードになるため、参加者数×通信量・待ち時間に注意。
