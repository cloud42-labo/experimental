# AFP｜過去会話を使う長期記憶方式

Notion `AFP-02-T02`。`AFP-EPIC-02`（Android化と本人所有の長期記憶基盤を成立させる）の方針
（会話記憶は「直近会話＋長期サマリー＋人物プロフィール」の階層型）を、具体的に実装可能な
方式へ落とす。対象は設計のみで、実装は `AFP-02-T04`（Androidアプリ骨格とGoogle認証の試作）
以降で行う。

保存先のファイル配置・形式・暗号化・削除復元は `AFP-02-T01`
（[data-model.md](./data-model.md)）が正本であり、本ドキュメントはそれに矛盾しない形で、
3層をどう生成し、会話開始時にどこから何を取得してLLMのプロンプトへ注入するかを定義する。
新規Vector DB／外部RAG基盤は作らない（`Minimum Solution`。家族向けの小規模PoCには過剰）。

## 1. 3層の役割分担

| 層 | 役割 | 更新頻度 | 保存先（data-model.md） |
|---|---|---|---|
| 直近会話（Recent Turns） | 直前のやり取りの文脈をそのまま維持する。代名詞・話題の継続に必須 | 毎ターン追記 | `conversation/{user_id}/{yyyy-mm-dd}.jsonl` |
| 長期サマリー（Long-term Summary） | 「前にも話したこと」を要約として保持し、全履歴を毎回送らずに参照できるようにする | バッチ的に増分更新（§3） | `summary/{user_id}.json` |
| 人物プロフィール（Person Profile） | 名前・関係・好み・注意点など、会話全体で変わりにくい属性 | 低頻度・プロフィール変化を検知した時のみ | `profile/{user_id}.json` |

3層は役割が異なるため統合しない。直近会話は「今の話の続き」、長期サマリーは
「過去に何があったか」、人物プロフィールは「この人は誰か」を担当する。

## 2. 会話開始時の文脈構成（Retrieval）

1ターンごとに全履歴を送らず、次の順でLLMのsystemプロンプトへ注入する文脈を組み立てる。

```
システムプロンプト
├── 1. 人物プロフィール（profile/{user_id}.json 全体。小さいため全量でよい）
├── 2. 長期サマリー（summary/{user_id}.json の最新版。§3の増分更新済みテキスト）
└── 3. 直近会話（当日分 conversation/{user_id}/{today}.jsonl の末尾N件、§4で既定N=12）
```

- 起動（アプリ再開・当日初回発話）時に1回だけ `profile` と `summary` を読み込み、
  アプリ内メモリに保持する。ターンごとに読み直さない（Drive APIの `files.get` を
  毎ターン呼ぶとレイテンシ・コストが増える。更新は書き込み側の操作後にのみ反映する）。
- 当日分の `conversation` jsonlは、当日分が存在すればアプリ起動時に末尾N件だけ読み込み、
  以後はアプリ内メモリ（バッファ）に追記していく。前日以前のjsonlファイルは起動時の
  通常フローでは読み込まない（§5「前日以前を参照したい場合」で補足）。
- 日付が変わった場合（`{yyyy-mm-dd}.jsonl` が切り替わるタイミング）、直近会話バッファは
  空から始める。その日の最初の発話では「長期サマリー」のみが前の文脈を担う。

## 3. 長期サマリーの生成トリガーと方法

全履歴を都度要約し直すと費用と時間が線形に増えるため、**増分更新**（前回サマリーに
今回分の差分だけを足し込む）方式を採る。

### トリガー条件（いずれかを満たした時に要約処理を実行）

1. 当日の `conversation` jsonlへの書き込みが一定件数（既定: 1日のやり取りが20ターンを
   超えた時点）に達した
2. アプリがバックグラウンドへ回った、またはユーザーが対話を終了した（セッション終了）
3. 日付が変わる直前（当日分を要約してから翌日分へ切り替える）

いずれも「毎ターン」ではない点が重要。毎ターン要約するとLLM呼び出しが倍になり、
Whisper→ChatGPT→OmniVoiceの応答レイテンシに要約処理が割り込んで会話体験を壊す
（README「応答待ち時間が会話体験を壊さないか」の仮説と衝突する）。要約はユーザーの
発話応答パスの**外側**（非同期・バックグラウンド）で行う。

### 生成方法

1. 直近の `summary/{user_id}.json`（既存の要約。無ければ空）を読み込む。
2. トリガー条件に達した時点までの当日分 `conversation` jsonl（未要約の差分区間のみ）を
   渡し、LLMに「既存サマリー＋今回の差分会話」から更新後サマリーを生成させる
   （要約専用の短いプロンプト。本体の対話プロンプトとは別呼び出し）。
3. 生成結果で `summary/{user_id}.json` を丸ごと置き換える（Drive APIに部分更新が無いため、
   data-model.md §2の方針と同じ read-modify-write）。
4. 要約が一定の長さ（既定: 2000文字）を超えた場合は、古い出来事ほど圧縮度を上げて
   短くする（「最近の出来事は詳しく、古い出来事は一行」という減衰方式）。具体的な圧縮
   アルゴリズムの調整は実装時のチューニング対象とし、本ドキュメントでは「古いものほど
   圧縮する」という方針のみを固定する。

### サマリーの内部構造（summary/{user_id}.json）

```json
{
  "updated_at": "ISO8601",
  "summary_text": "直近の出来事を優先し古いものを圧縮した自然文の要約",
  "last_summarized_through": "ISO8601（この時点までの会話を要約済み）"
}
```

`last_summarized_through` を持つことで、次回の増分更新時に「どこから先が未要約か」を
機械的に判定できる（conversation jsonl側のタイムスタンプと比較する）。

## 4. 直近会話の末尾N件という設計の根拠

- N=12（直近6往復）を既定値とする。シニア・子ども向けの短い応答（README「返答は
  1〜3文程度」）を前提にすると、12件でも十分な文脈量になる一方、プロンプトが肥大化
  しすぎない。
- Nは固定件数ではなく「直近の文字数が一定（既定2000文字）を超えたら件数を減らす」
  形でも良いが、実装の複雑さに対して効果が小さいため、本設計では件数固定（N=12）を
  初期値とし、実機検証（`AFP-02-T04`以降）で必要なら調整する。

## 5. 前日以前を参照したい場合（将来拡張・本Taskのスコープ外）

「先週話した◯◯の話、覚えてる？」のような明示的な遡り要求への対応は、長期サマリーが
拾えなかった場合のフォールバックとして、`conversation/{user_id}/` 配下の過去日付jsonlを
日付逆順に検索する拡張が考えられる。ただし全文検索インデックスを別途持たない
（`Minimum Solution`に反する）ため、本Taskでは「長期サマリーに含まれる範囲で答える」
ことを既定動作とし、過去jsonlへの遡り検索は別Taskとして扱う。

## 6. AFP-02-T01（data-model.md）との整合確認

- ファイル配置・形式・暗号化・削除復元は data-model.md がそのまま正本（本ドキュメントは
  参照するのみで再定義しない）。
- `conversation` / `profile` / `summary` はdata-model.md §3の方針により暗号化しない
  （`voice` のみ暗号化対象）。本ドキュメントの読み書きもこの前提に従う。
- `summary/{user_id}.json` の内部スキーマ（§3）はdata-model.md が「中身のスキーマは
  `AFP-02-T02`で確定する」としていた委任先であり、本ドキュメントで確定した。
- 保存先パスの命名・親フォルダ構成に変更は加えていない。

## まとめ（Acceptance Criteriaとの対応）

- 直近会話・長期サマリー・人物プロフィールの3層構成 → §1
- 全履歴を毎回送らずに前の会話を自然に参照できる構成 → §2（起動時1回読み込み＋当日分末尾
  N件という非線形コスト設計）
- 各層の生成・取得トリガー → §2（取得）・§3（長期サマリーの生成トリガー）
- `AFP-02-T01` との保存先の矛盾なし → §6
